# 数据采集与样本构造

> 状态：论文事实 + 项目设计草案
>
> 本文档聚焦两件事：
> - 如何获取适合 Suphx 风格训练的数据
> - 如何把原始牌谱转换为真正可训练的样本合同

## 1. 目标

Tenpai 的数据工作不应停留在“下载天凤 JSON 并存库”。

真正服务训练的目标是：
- 获取高质量四人立直麻将牌谱
- 生成五类动作监督学习样本
- 生成 `global reward prediction` 所需的序列样本
- 为离线评估与后续在线评测保留稳定切分

## 2. 数据来源

### 2.1 首选来源

如果目标是尽量贴近 `Suphx`，首选数据来源应为天凤（Tenhou）公开牌谱。

原因：
- 论文结论基于 Tenhou 环境
- 在线评测语境与 `record rank`、`stable rank` 一致
- 监督学习与在线表现更容易形成闭环

### 2.2 文档层面的保守原则

本文档只确认“可作为候选来源”的方向，不把外部接口细节写成永久稳定契约。

后续若实现抓取器，应把这些内容放到代码或工具文档中：
- 实际下载地址
- API 参数
- 速率限制
- 重试策略

## 3. 不同层级的数据形态

为了避免“原始数据”和“训练数据”混淆，建议把数据分成三层。

### 3.1 原始层

原始层只负责保存外部来源的原始内容，例如：
- 原始牌谱标识
- 原始牌谱正文
- 基本元信息

这一层的目标是可追溯，而不是直接训练。

### 3.2 解析层

解析层把原始牌谱转成结构化事件流，例如：
- 开局信息
- 配牌
- 摸牌
- 弃牌
- 立直
- 吃碰杠
- 和牌 / 流局
- 分数变化

这一层的目标是统一语义，让训练和评估共用同一套事件解释。

### 3.3 样本层

样本层才是训练直接消费的数据，至少应包括：
- `discard samples`
- `riichi samples`
- `chi samples`
- `pon samples`
- `kan samples`
- `reward predictor sequences`

如果没有样本层，后续训练文档中的模型拆分就无法真正落地。

## 4. 训练数据合同

### 4.1 弃牌样本

每当轮到目标玩家弃牌，并且存在合法弃牌动作时，生成一条 `discard sample`。

建议字段：
- `log_id`
- `game_index`
- `round_index`
- `seat`
- `turn_index`
- `state_features`
- `legal_actions`
- `chosen_action`
- `round_context`
- `final_game_outcome`

关键点：
- `chosen_action` 来自人类专家真实动作
- `legal_actions` 用于过滤不合法输出和做离线评估
- `round_context` 用于连接局内状态与整场目标

### 4.2 立直样本

仅在“当前合法可立直”时生成 `riichi sample`。

建议字段：
- `state_features`
- `is_riichi_available`
- `chosen_action`
- `shanten_context`
- `score_context`

如果不限制在“可立直状态”，就会得到大量无意义负样本。

### 4.3 吃 / 碰 / 杠样本

这三类样本都属于“条件触发决策”，必须只在动作合法时生成。

建议分别记录：
- 触发来源玩家
- 触发牌
- 候选副露形式
- 实际选择
- 触发前后局况

尤其是 `chi sample`，可能不只是“吃 / 不吃”，还要区分不同吃法候选。

### 4.4 奖励预测序列样本

`global reward prediction` 不是单步分类任务，需要单独的数据结构。

建议序列样本至少包含：
- 整场对局的 round 序列
- 每一局结束后的分数
- 当前顺位与最终顺位
- 庄家轮转、本场数、立直棒数
- 最终回报标签

这类样本不应与动作样本混在同一张表里处理。

## 5. 标签定义原则

### 5.1 监督学习标签

监督学习标签以人类真实动作作为主标签：
- 打了哪张牌
- 是否立直
- 是否吃、碰、杠

不要把“规则引擎推荐动作”直接当成人类标签替代品。

### 5.2 辅助标签

为了支持分析和切片评估，可以额外生成辅助标签，例如：
- 向听数
- 是否听牌
- 是否有人立直
- 是否末局
- 当前名次
- 与上家 / 下家点差

这些辅助标签更适合：
- 数据分析
- 分桶评估
- curriculum 或采样权重策略

### 5.3 Oracle 相关标签

若后续要尝试 `oracle guiding`，建议新增单独标签管道，而不是污染主监督标签。

例如可额外记录：
- 完整信息下的危险度估计
- 完整信息下的潜在最优收益路径
- 供辅助损失使用的教师信号

在这部分真正实现前，文档里应只把它写成实验扩展。

## 6. 数据切分

### 6.1 基本切分

推荐至少切为：
- `train`
- `validation`
- `evaluation`

切分原则：
- 同一整场牌谱只属于一个集合
- 不要把同一牌谱拆到多个集合中
- 评估集合应固定，避免反复调参污染

### 6.2 为什么不能只随机切动作样本

如果直接对单步样本做随机切分，会产生明显泄漏：
- 同一牌局的前后动作可能同时出现在训练集和验证集
- 模型能记住特定对局上下文，导致指标虚高

因此应优先按整场牌谱切分，再派生样本。

## 7. 数据质量约束

### 7.1 必须过滤的问题数据

建议至少过滤：
- 非四人立直麻将数据
- 事件流不完整的数据
- 无法重建合法动作集的数据
- 对局结果缺失的数据

### 7.2 需要重点统计的质量指标

建议持续记录：
- 原始牌谱数
- 成功解析率
- 成功生成样本率
- 各动作样本数量分布
- 不同桌型 / 规则集分布
- 末局样本比例

这些统计会直接影响训练可行性，不能等到模型训练失败后再回头补。

## 8. 特征生成原则

### 8.1 与训练文档保持一致

样本层输出的 `state_features` 应与 `docs/zh/04-TRAINING.md` 保持同一套编码思路，优先包括：
- 手牌计数
- 弃牌信息
- 副露信息
- 宝牌信息
- 场况信息
- 点数和顺位信息
- 可解释的 look-ahead features

### 8.2 不要过早引入重型变换

在基线跑通前，不建议把以下内容写成默认数据流程：
- 大规模等价牌型增强
- 激进的对称变换
- 复杂序列裁剪增强

这些都可以作为实验项，但不应先于“稳定样本合同”存在。

## 9. 存储建议

### 9.1 存储目标

存储层要同时满足：
- 可追溯
- 可批量读取
- 可统计分析
- 可跨语言消费

### 9.2 设计建议

当前仓库还没有稳定实现，因此这里只给方向，不写死具体表结构：
- 原始牌谱与样本层分开存储
- 元信息、事件流、样本表分开建模
- 保留版本号，避免不同解析逻辑混用

如果后续采用 DuckDB，它适合承担：
- 本地分析
- 列式读取
- Python / Go 双侧访问

但“使用 DuckDB”不等于“只要把 JSON 丢进 DuckDB 就完成数据工程”。

## 10. 数据流水线建议

推荐的最小可行流水线：

```text
原始牌谱
    -> 结构化事件流
    -> 动作合法性重建
    -> 五类动作样本导出
    -> reward predictor 序列样本导出
    -> train / validation / evaluation 切分
```

只有这一链路跑通后，训练文档中的多模型设计才真正具备实现条件。

## 11. 当前仓库状态下的结论

截至目前，仓库文档已经讨论了训练、架构和验证方向，但尚未看到稳定的数据流水线实现。

因此本文档应承担的角色是：
- 约束后续数据工程边界
- 明确训练真正需要的样本形态
- 防止项目继续停留在“只有原始 JSON，没有训练样本合同”的阶段
