>

## 1. 架构说明方式

为避免文档和仓库状态脱节，本文档分三层描述：
- `当前现状`：仓库里已能直接确认的内容
- `目标架构`：为了复现论文与推进项目而建议采用的模块划分
- `实现缺口`：从现状走到目标架构还缺哪些部分

## 3. 目标架构

### 3.1 总体目标

Tenpai 的合理目标不是先做一个庞杂的一体化系统，而是围绕论文 `Suphx` 建立三个松耦合层：

```text
数据层 -> 训练层 -> 评估层
```

它们的职责应当是：
- 数据层：获取和整理牌谱，生成训练样本
- 训练层：训练多个动作模型与辅助模型
- 评估层：离线评估、回放评估、在线评测支持

### 3.2 推荐逻辑架构

```text
┌─────────────────────────────────────────────┐
│                 Tenpai                      │
├─────────────────────────────────────────────┤
│ Data Pipeline                               │
│ - 牌谱抓取 / 导入                           │
│ - 牌谱解析                                 │
│ - 监督学习样本构造                         │
│ - 序列样本构造                             │
├─────────────────────────────────────────────┤
│ Training                                    │
│ - discard / riichi / chi / pon / kan 模型  │
│ - reward predictor                         │
│ - 监督学习                                 │
│ - 自博弈强化学习                           │
├─────────────────────────────────────────────┤
│ Evaluation                                  │
│ - 离线指标                                 │
│ - 回放评估                                 │
│ - 在线评测支持                             │
└─────────────────────────────────────────────┘
```

这里特意把“验证层”改成“评估层”，因为目前更重要的是：
- 先把论文对齐的训练与评估闭环建起来
- 再决定是否需要单独的 GUI 或客户端自动化模块

## 4. 数据层

### 4.1 目标职责

数据层的职责不是只保存原始牌谱，而是生成可训练的数据合同。

至少应覆盖：
- 原始牌谱抓取或导入
- 结构化牌局解析
- 五类动作标签提取
- round 级别序列数据提取
- 训练 / 验证 / 评估数据切分

### 4.2 推荐输出

数据层建议输出两大类数据：

1. `动作样本`
   - 打牌样本
   - 立直样本
   - 吃样本
   - 碰样本
   - 杠样本

2. `序列样本`
   - 用于 `global reward prediction`
   - 包含局进展、点数变化、名次变化、终局结果等

### 4.3 技术实现建议

Go 适合承担：
- 大规模抓取与导入
- 结构化解析
- 数据库存储与批量处理

但这只是技术方向，不代表当前仓库已具备这些模块。

## 5. 训练层

### 5.1 训练层目标

训练层应以 Suphx 的方法分解为核心约束：
- 不是单模型包办所有动作
- 不是先写死 `PPO + MCTS`
- 不是默认 Transformer 主干

第一阶段更合理的训练层划分为：
- `discard_model`
- `riichi_model`
- `chi_model`
- `pon_model`
- `kan_model`
- `reward_predictor`

### 5.2 推荐训练职责

训练层至少要支持：
- 样本读取与批处理
- CNN 风格模型训练
- 多模型独立评估
- 模型版本管理
- 自博弈样本生成接口

### 5.3 Python 的定位

Python 在这里适合承担：
- 模型原型验证
- 训练循环实现
- 指标统计与可视化
- 实验配置管理

是否长期保留 Python 作为主训练语言，可以后续再评估；但在当前阶段，它仍是最务实的训练层选择。

## 6. 评估层

### 6.1 为什么用“评估层”而不是“验证层”

之前文档把 Rust + 雀魂 OCR + 鼠标自动化写成主线，容易让项目重心偏离论文复现。

更合理的定义是：
- 先解决模型是否真的学到了有效策略
- 再考虑如何把模型接到外部运行环境

因此，评估层优先应包含：
- 离线指标评估
- 回放式决策比较
- 自博弈对战评估
- 在线评测接口

### 6.2 在线评测优先级

如果目标是与论文结论对齐，在线评测说明应优先围绕天凤：
- 论文报告基于 Tenhou 环境
- `record rank` 与 `stable rank` 讨论也依赖该平台语境
- 能更自然地连接训练数据来源与最终表现

雀魂相关验证若要保留，建议降级为独立实验方向，而非核心架构的一部分。

### 6.3 Rust 的可能定位

Rust 仍然有价值，但更适合作为后续增强能力：
- 高性能规则计算
- 推理服务封装
- 回放评估工具
- 可能的桌面客户端或可视化工具

在没有对应代码前，不应写成“当前验证层已经完成”。

## 7. 模块边界

### 7.1 数据层与训练层边界

边界应是“数据合同”而不是“临时脚本”。

建议明确：
- 输入数据格式
- 每类动作样本字段
- 序列样本字段
- 切分策略与版本号

这样才能避免：
- 数据解析逻辑散落在训练代码里
- 同一牌谱被不同脚本以不同方式解释

### 7.2 训练层与评估层边界

边界应是“模型工件 + 评估协议”。

建议明确：
- 模型命名与版本策略
- 推理输入输出格式
- 指标定义
- 回放评测协议

在这之前，不建议提前承诺固定的跨语言模型导出格式。

## 8. 当前不应写死的技术决策

以下内容可以作为候选项，但不应继续在文档中写成定论：
- `TensorFlow SavedModel` 是 Python 到 Rust 的默认桥接方式
- 训练完成后必须进入雀魂验证流程
- 项目必须有 GUI 客户端
- 当前已经存在 `config/`、`data/`、`models/` 等目录

如果未来真的采用这些设计，应以实际代码和目录为准再补文档。

## 9. 建议目录演化

### 9.1 当前建议的文档级模块划分

在代码尚未完整落地前，建议先用文档把模块边界讲清楚：
- `ARCHITECTURE.md`：只描述现状、目标和缺口
- `TRAINING.md`：只描述训练设计
- `DATA_COLLECTION.md`：只描述数据来源与样本构造
- `EVALUATION.md`：后续新增，描述离线与在线评估
- `PROJECT_STATUS.md`：后续新增，明确“已实现 / 计划中”

### 9.2 未来代码目录建议

等真正开始实现后，可以再让目录自然收敛为类似结构：

```text
<repo>
├── docs/
├── data_pipeline/
├── training/
├── evaluation/
└── tools/
```

这里只表达模块意图，不把目录名写成已经存在的仓库现实。

## 10. 实现缺口

从当前仓库走向目标架构，至少还缺：
- 牌谱获取和解析实现
- 训练样本生成器
- 五个动作模型的训练脚本
- reward predictor 训练流程
- 离线评估脚本与指标定义
- 统一配置与实验记录机制

这些缺口应被视为项目主任务，而不是继续扩写假定已存在的部署说明。

## 11. 架构决策原则

后续补代码和补文档时，建议遵守以下原则：
- `先事实，后规划`：先写清现状，再写目标
- `先数据合同，后训练细节`：没有稳定样本格式，训练层很难稳定推进
- `先离线评估，后在线接入`：先证明模型有价值，再接外部平台
- `先论文对齐，后额外扩展`：优先把 Suphx 主线复现清楚
