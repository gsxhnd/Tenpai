# 雀魂验证实验

> 状态：实验性扩展
>
> 本文档不再把雀魂验证写成项目主线，也不再假设相关 Rust 客户端、OCR、输入模拟系统已经完成。
> 如果项目目标是尽量贴近 `Suphx` 论文，主线评估应优先围绕天凤与离线评估展开；雀魂方向只能视为后续实验。

## 1. 文档定位

### 1.1 这份文档解决什么问题

本文档只讨论一个可选方向：
- 如果未来希望把模型接到雀魂环境做额外实验，可能需要哪些能力与风险控制

它不表示：
- 当前仓库已经具备可运行的雀魂验证系统
- 雀魂验证是论文复现的必要路径
- 项目应该优先投入客户端自动化而不是训练与评估闭环

### 1.2 为什么降级为实验扩展

原因很直接：
- `Suphx` 论文的在线评测主语境是天凤，不是雀魂
- 当前仓库尚未出现支撑该方向的实现代码
- GUI 自动化、OCR、输入模拟会引入额外工程复杂度和合规风险

## 2. 与论文主线的关系

### 2.1 主线评估仍应优先考虑什么

如果目标是与论文主线保持一致，优先级应为：
- 先完成监督学习样本流水线
- 再完成多模型训练与离线评估
- 再建立自博弈和论文术语对应的评测方式
- 最后才考虑接外部平台做附加实验

### 2.2 雀魂方向适合研究什么

雀魂验证更适合作为以下研究问题的实验场：
- 模型在不同 UI 和交互环境下是否仍稳定
- 非论文原生平台上的泛化能力如何
- 规则引擎、状态解析、实时推理的工程可行性如何

这类问题很有价值，但它们不应压过训练主线。

## 3. 风险与边界

### 3.1 合规风险

任何涉及以下能力的方案都存在明确风险：
- 屏幕抓取
- OCR 解析
- 鼠标键盘输入模拟
- 自动对局代理

因此，后续如果继续探索，必须先自行确认：
- 平台服务条款
- 账号风险
- 是否仅在离线、演示、测试环境中使用

本文档不提供任何“默认可安全上线使用”的暗示。

### 3.2 工程风险

即使不考虑合规，雀魂方向本身也有较高不稳定性：
- UI 更新会破坏模板匹配或区域定位
- 分辨率、缩放、语言设置会影响识别
- 网络波动会使状态同步和动作执行时机更难控制
- 实时系统中的单次误识别可能导致整局状态漂移

### 3.3 项目管理风险

在当前阶段过早投入这个方向，最可能的后果是：
- 训练主线迟迟无法闭环
- 资源被 UI 自动化细节消耗
- 文档和代码再次出现“实现想象大于实际能力”的问题

## 4. 如果未来继续做，需要的最小模块

这部分只描述能力边界，不代表现有实现已经存在。

### 4.1 状态采集

需要解决：
- 游戏窗口或画面获取
- 手牌、弃牌、副露、宝牌、点数等区域定位
- 当前可选动作识别

### 4.2 状态重建

需要解决：
- 将图像或文本信号转成统一 `GameState`
- 做合法性校验
- 在识别失败时有回退和纠错策略

### 4.3 决策接入

需要解决：
- 将重建状态映射到训练时使用的特征格式
- 调用模型推理
- 合法动作过滤

### 4.4 动作执行

需要解决：
- 决策映射到 UI 操作
- 点击前后的状态确认
- 超时与异常回滚

### 4.5 运行日志

需要解决：
- 保存每次识别结果
- 保存每次模型输入输出
- 保存失败案例截图与上下文

没有这类日志，后续几乎无法定位错误来源。

## 5. 推荐的实验路线

### 5.1 阶段一：纯离线回放

先不要接真实客户端。

优先做：
- 从历史牌谱回放中重建状态
- 用模型在每一步给出建议动作
- 对比人类动作与模型动作差异

这样可以先验证：
- 特征编码是否一致
- 推理接口是否稳定
- 多模型协同是否合理

### 5.2 阶段二：静态界面识别

如果一定要走雀魂方向，下一步也应先做静态图像识别实验，而不是直接自动打牌。

建议先回答：
- 固定分辨率下能否稳定识别关键区域
- 牌面识别准确率是否足够高
- 点数、场况、操作按钮是否能稳定解析

### 5.3 阶段三：只读模式

在真正尝试输入模拟前，应先做只读模式：
- 观察对局
- 实时解析状态
- 输出建议动作
- 不执行点击

这个阶段能帮助确认识别链路是否可靠，同时降低风险。

### 5.4 阶段四：受控实验

只有在前面阶段稳定后，才值得评估是否进行受控自动化实验。

即使进入这一阶段，也建议：
- 使用专门测试账号
- 严格限制实验场景
- 完整保留日志与录像
- 随时准备终止实验

## 6. 与当前仓库的关系

截至当前仓库状态：
- 文档层面对雀魂方向曾经写得过于具体
- 但仓库中尚未看到对应的 Rust 客户端、图像资源、OCR 模块或输入模拟实现

因此更准确的说法应是：
- 雀魂验证目前只是一个可能的未来实验方向
- 它不构成当前项目的实现现状
- 它不应替代论文主线评估设计

## 7. 推荐的文档策略

为了避免读者误解，后续文档中提到雀魂时建议统一使用以下口径：
- “实验性扩展”
- “非论文主线”
- “存在合规与工程风险”
- “当前仓库未实现”

不建议继续使用以下表述：
- “训练完成后进入雀魂验证阶段”
- “Rust 验证层负责雀魂实战”
- “系统已具备 OCR 与自动操作能力”

## 8. 当前结论

对 Tenpai 来说，雀魂方向不是不能做，而是不应该在当前阶段抢占主线优先级。

更合理的顺序是：
1. 先把数据流水线做实
2. 先把 `Suphx` 对齐的训练闭环做实
3. 先把离线评估和论文术语体系做实
4. 再决定是否值得投入雀魂实验
