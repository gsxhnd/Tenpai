# 开发指南

> 状态：项目设计草案 + 当前阶段建议

本文档只讨论当前仓库阶段真正有帮助的开发顺序、环境基线和协作约束。
它不再假设仓库里已经存在完整的 Go / Python / Rust 子模块目录。

## 1. 先读什么

开始写代码前，建议先按以下顺序阅读：

1. [ARCHITECTURE.md](./ARCHITECTURE.md)
2. [DATA_COLLECTION.md](./DATA_COLLECTION.md)
3. [TRAINING.md](./TRAINING.md)
4. [MAJSOUL_VALIDATION.md](./MAJSOUL_VALIDATION.md)（仅在做实验扩展时阅读）

这样可以避免：
- 先写实现，后发现文档目标不一致
- 把实验方向误当成主线需求
- 把未实现模块写进代码结构假设里

## 2. 当前仓库已知基线

当前仓库可以直接确认：
- Go 配置见 `go.mod`
- Rust 工作空间配置见 `Cargo.toml`
- Python 项目配置见 `pyproject.toml`
- 参考论文位于 `docs/pdf/2003.13590v2.pdf`

当前仓库尚未确认：
- 稳定的数据流水线实现
- 多模型训练代码
- 统一的离线评估脚本
- 可运行的外部平台验证客户端

因此，开发工作的重点应先放在补主线缺口，而不是扩写外围系统。

## 3. 推荐开发顺序

### 3.1 第一优先级：数据合同

先定义并实现：
- 原始牌谱如何解析成结构化事件流
- 如何导出五类动作样本
- 如何导出 `reward predictor` 序列样本
- 如何做整场级别的数据切分

这是当前最关键的地基。

### 3.2 第二优先级：监督学习基线

建议先实现最小可行训练闭环：
- 优先完成 `discard_model`
- 保证样本读取、特征编码、训练循环能跑通
- 建立最基本的离线评估指标

如果连这一步都还没跑通，不建议过早引入复杂训练策略。

### 3.3 第三优先级：多模型扩展

在打牌模型稳定后，再逐步加入：
- `riichi_model`
- `chi_model`
- `pon_model`
- `kan_model`
- `reward_predictor`

### 3.4 第四优先级：强化学习与实验项

只有当监督学习基线和离线评估都稳定后，才建议继续：
- 自博弈 RL
- `oracle guiding`
- `pMCPA`
- 雀魂实验验证

## 4. 环境建议

### 4.1 语言版本基线

建议以仓库当前配置为准：
- Go：`go.mod` 当前为 `1.25`
- Rust：`Cargo.toml` 当前为 `1.86`
- Python：`pyproject.toml` 当前为 `>=3.12`

### 4.2 环境准备原则

当前阶段优先保证：
- 能读取和处理牌谱数据
- 能运行最小训练脚本
- 能执行最基本的静态检查和测试

不要先为尚未存在的部署、GUI、OCR、自动化链路准备复杂环境。

## 5. 代码组织建议

在实现真正开始前，建议先按职责组织代码，而不是提前复制一个庞大目录树。

推荐模块边界：
- `data pipeline`
- `training`
- `evaluation`
- `tools`

每个模块都应围绕单一目标建设：
- 数据模块输出稳定样本合同
- 训练模块消费样本并产出模型工件
- 评估模块复用同一特征和指标定义

## 6. 文档与代码同步规则

后续开发时建议遵守：
- 只有目录或命令已经存在，文档里才把它写成现状
- 设计草案必须显式标注为“计划中”或“实验性”
- 如果实现偏离论文主线，应明确写出差异原因

这条规则是为了避免项目再次出现“文档像完成了，代码其实还没开始”的问题。

## 7. 最小验证方式

当前阶段更适合做的验证包括：
- 数据解析单元测试
- 样本生成一致性检查
- 特征编码回归测试
- 训练脚本的最小烟雾测试

相比之下，以下内容都应后置：
- 部署手册
- GUI 验证链路
- 外部平台自动化

## 8. 协作建议

如果后续多人协作，建议按主线拆任务：
1. 数据解析与样本合同
2. 特征编码与数据读取
3. 打牌模型监督学习基线
4. 离线评估与指标体系
5. 其他动作模型与实验项

这种拆法更贴近当前项目真实阶段，也更便于验证每一步是否真的前进。
